  Size arithmetic: the diff is 68,469 bytes, about 66.9 kB. sqrt(66.9) is about
  8.18, plus 1 is 9.18, so N = min(9, 10) = 9. Findings follow, 11 in all.

  - **Wasted work on every product page view.** `load_company_data` runs
  `forecast_product` for every product in the company and also builds
  `build_overview(results, {})`. `product_screen` never reads `data.overview`,
  and it needs the result of only one product. A page for one of 50 products
  with 104 weeks each computes all 50 and an unused overview. Consider a lazy or
  single-product path, or drop the overview from this call.
  - **Unknown product numbers cost a full forecast before the 404.** The 404
  check is `data.results.get(product_number)`, so a mistyped or foreign number
  still triggers the whole-company calculation. Check the product's existence
  against the cheap products query first.
  - **Latest week is queried twice per request.** `header_context` calls
  `queries.latest_data_week(company)`, and `load_company_data` calls it again
  for `latest_week`. The test comment even counts "1 for the header" as a
  separate query. Pass the already-loaded week into the header context instead
  of querying twice.
  - **Linear scan for the product, with a latent bare `StopIteration`.** `next(p
  for p in data.product_list if p.product_number == product_number)` is O(n)
  and has no default. A mismatch between `results` and `product_list` would
  surface as a `StopIteration` inside the view (a 500), not a 404. Build a dict
  keyed by product number in `CompanyData`, or look the product up once.
  - **The trust label is rendered twice and the `large` parameter is dead.** The
  label appears in the page header and again in the "Kan du stole på
  prognosen?" panel, so screen readers announce "Middels" or "Lav" twice. Both
  includes pass `large=True`, so the non-large `<svg width="12">` branch and the
  `{% if large %}` logic in `_trust_label.html` are never used. The test even
  asserts both pills are 14×14. Either use the small variant somewhere, such as
  the list, or remove the parameter. Also decide whether the duplicate label is
  intended for assistive tech.
  - **Keyboard and landmark problems from `tabindex="0"` on the list and detail
  regions.** Up to 900 px the CSS removes the scroll frames (`overflow:
  visible`), but the `<nav>` and `<main>` keep `tabindex="0"`. That leaves two
  focusable but non-scrollable stops on narrow screens. Neither region has a
  visible `:focus` or `:focus-visible` style in the CSS. A `nav` that wraps a
  data table is also a questionable landmark. Tests assert the tab stops exist
  but never check that they are conditional or visibly focused.
  - **Colour contrast is asserted only by token name.** The pills (amber on
  amber-tint, red on red-tint, green on green-tint), the blue link on blue-tint,
  and the red icon outline on a surface fill are never contrast-checked. The
  tests only compare strings like `var(--color-amber)`. UX-DR20 and NFR-11 (the
  accessibility requirement the tests cite) need a computed ratio check against
  the token values, including the `.selected` row (`blue-ink` on `blue-tint`).
  - **Business rule in the template.** `{% if not
  result.suggested_order_quantity %} quantity-ink{% endif %}` decides in the
  template that 0 and None are ink-coloured. This is the "0 vs missing" rule the
  tests guard, yet it lives outside `explanation/decision.py` (AD-4 says texts
  and decisions are placed in the template, not made there). Return an
  `is_order` flag from `DecisionTexts` and use that.
  - **Hard-coded literals in the new CSS where tokens are used elsewhere.** The
  rules use `14px`, `10px`, `6px`, `2px 10px 2px 8px`, `4px 12px 4px 10px` and

  tests otherwise verify.
  - **Brittle and thin tests.**

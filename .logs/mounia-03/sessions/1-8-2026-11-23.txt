  number is echoed back and a very long password is hashed. If throttling is out
  of scope for v1, write that down as a decision. Otherwise add it, with a
  test.

  - **Logged-in pages can be cached, so Back after logout may show another
  company's data.** `product_overview` and the other logged-in pages set no
  `Cache-Control: no-store` or `never_cache`. On a shared machine, Back after
  "Logg ut" can show the cached product list. The story cites NFR-10 ("Reload,
  Back"), but no test or header covers this case.

  - **The logout test cannot show that the session died on the server.**
  `session_ids()` only reads the client's cookie, and it also returns `None` for
  a deleted or empty cookie. No test checks that the `Session` row is gone, or
  that replaying the old session id after logout fails. The test only proves the
  cookie was dropped, not that the session ended.

  - **The shell test skips the new products page.** In
  `tests/test_app_shell.py`, `PAGES` swaps `web/start.html` for `web/login.html`

  and no external src/href therefore don't run on the logged-in page. That page
  also uses the new app header.

  - **The product table has no empty state and may overflow.**
    - `products.html` has a `{% for %}` with no `{% empty %}`. A company with no
  products gets a header-only table. The test for a company without sales weeks
  only checks the header, not the table body.

  `overflow-wrap` or `word-break` handling for long product names at 320 px.
    - The table has no `<caption>` or accessible name.

  `tests/test_isolation.py` only flags `Product.objects`-style names and a fixed

    - Templates are not scanned, so `{{ company.products.all }}` passes.
    - `node.attr in MANAGER_NAMES` flags any attribute called `products` in
  `web/`, including unrelated ones.
    - The seed reader and loader are exempt wholesale.
    - Say how much this test is meant to guarantee, or tighten it.

  - **The isolation test can fail by chance.**
  `test_each_company_sees_only_its_own_data` asserts that strings such as
  `"7372"` and `"8481"` are absent from the page. Every page now carries a
  random masked CSRF token (in the logout form), and the token can contain those
  digits. The chance is tiny but not zero. Strip the tokens first, as
  `test_login.py` already does with `TOKEN.sub`.

  - **`test_manage` now runs the whole login suite in a subprocess.** The
  settings-module check points at `tests/test_login.py`. The old target was a
  database-free page test. The new file needs the `two_companies` fixture and
  the database. It also imports `test_error_pages` as a top-level module and
  reads `catalogue_text(...)` at import time. A catalogue or DB problem would
  now break an unrelated test with a confusing failure. Pick a small
  database-free test file for that check instead.

  - **A failed CSRF check on `/` gives no feedback to a logged-in user.** In
  `csrf_failure`, any failed POST to the login path by an authenticated user is
  silently redirected to the overview. This covers both the double submit and a
  stale token. A user who deliberately tries to log in as another company with
  an expired form is shown their old company's products, with no message. Limit
  the redirect to the double-submit case, or show a notice.

  - **Sessions have no declared lifetime, and the login redirect has no `next`
  handling.** The README and settings say nothing about session age or
  inactivity timeout. With `redirect_field_name = None`, an expired session
  always lands on the overview. A bookmark to a later page, such as the Story
  2.7 product page, loses its destination. Either record this as a deliberate
  trade-off or add a safe `next`, checked with
  `url_has_allowed_host_and_scheme`.

  - **The failed-login form has gaps.**
    - Neither input has `aria-invalid="true"`, and focus does not move to the
  error or the first field after a failed submit.
    - The customer-number field is `type="text"` with no `inputmode="numeric"`.
  That is a small cost on the phone testing this story targets.
    - `.button-primary` has no disabled or "sending" state, so the double-submit
  protection is server-side only.

  - **The new global CSS will leak into later screens.** Bare `label`,

  future form, including the Epic 3 settings fields and the switch. They also
  add a 16px top margin to every label. Scope them, for example to `.form`.

  - **Header text is hard-coded and awkward.**

  hard-codes the string.
    - The tests take the login error from the EXPERIENCE.md Message Catalogue,

  `views.LOGIN_ERROR` is also a separate hard-coded copy of the catalogue text.
    - The README and `login.html` say the header shows the "latest registered
  week". `display.header_week_label` is a bare f-string with no tests for week
  padding or invalid values.

  - **The README's LAN instructions don't mention plain-HTTP risk.** The new
  "Test på en ekte telefon" section now has the user log in over unencrypted
  HTTP on the local network, with `0.0.0.0` binding. It doesn't say that
  passwords and the session cookie travel in clear text, or that the test
  passwords are public. It also doesn't say that Safari may need the

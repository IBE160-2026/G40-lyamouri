# Review: Calculation Rules and Reference Examples

Scope: `prd.md` §3 Glossary, FR-5 to FR-19, §5 (R-1 to R-14, E1 to E14) and §9. Every example was recomputed in double precision from the rules as written, not from the stated results. Severity: **critical** = a Must rule allows different numbers; **high** = a conflict or an undefined result; **medium** = a test, display or data decision is left open; **low** = wording.

**Verdict:** the arithmetic is right in all 14 examples (14 correct, 0 wrong, 0 ambiguous). The rules still leave decisions to the implementer: 1 critical, 4 high, 8 medium and 6 low findings. When a rule is fixed, add its example from §3 to §5.6 and to the reference spreadsheet.

## 2. Rule findings

These rules were checked and are clear as written, but each still lacks an example (see §3): exponential smoothing over skipped weeks (R-4), the outlier rule at the start of the history and after a stockout gap (R-10), a level shift across stockout weeks (R-11), a week number with only stockout weeks (R-14 step 4), weeks of cover at forecast 0 (R-12), and the 8-week boundary (FR-18, E12).

**F1 · critical · R-10/R-11, FR-17, glossary «Level shift».** Quote: "Three or more unusual weeks in a row (counting valid weeks only) are a level shift: they stop being unusual weeks, are always kept in the calculation, and count in later baselines." Problem: the processing order is not defined, and three readings fit the text. (A) One forward pass: the third flagged week turns the run into a level shift at once, the count restarts, and the next week is checked against the new baseline. (B) As A, but a flagged week right after a level-shift week joins it ("or more"). (C) The weeks of an open run are checked against the old baseline and classified when the run ends. On 20, 22, 21, 50, 52, 51, 110, 50 with unusual weeks excluded, the moving average 3 is 51.0 under A and 70.333 under B and C. After a lasting rise, C marks every later week as a level shift, while A and B mark three. Re-checking earlier weeks after a reclassification never settles on E9. Fix: write R-10/R-11 as pseudo-code (one forward pass over valid weeks, no re-checking), choose A or B explicitly, and add M1.

**F2 · high · Glossary «Confidence label», FR-19, FR-16, AG-1, SM-1.** Quote: "Low: fewer than 12 valid weeks. Medium: 12 to 103 valid weeks, or any active warning." Problem: there is no precedence, so E7's product (4 valid weeks and a stockout warning) is both Low and Medium. A product with 12 or more valid weeks and no forecast (window 12, 11 calculation weeks) is Medium by the thresholds and Low by FR-19 ("A product without a forecast (FR-8) is labelled low"). Excluding unusual weeks can then change the label, against FR-16 ("switching the setting does not change the confidence label by itself"). The label has no rule in §5, although AG-1 says labels come only from §5. No example covers it, although SM-1 claims to validate FR-19. Fix: add R-15 as an ordered rule (1. no forecast or fewer than 12 valid weeks → Low; 2. fewer than 104 valid weeks or any active warning → Medium; 3. otherwise High), narrow the FR-16 sentence, and add M6.

**F3 · high · §9 SM-1, NFR-2, DR-6, SM-C2, FR-9, FR-17, E14.** Quote: "100% of the reference examples E1 to E14 pass as automated tests" and "Should and Could items start only after the Must scope passes SM-1 and SM-3". Problem: E14 tests R-14, which is a Should rule, so the Must gate cannot pass before a Should item is built, and no Should item may start before the gate passes. E14 uses a 4-week cycle, so it cannot run against code fixed to 52 week numbers. FR-9 and FR-17 refer to reference examples for the seasonal and level-shift test products, which §5.6 does not contain. Fix: split SM-1 into Must examples (E1–E13 plus new ones) and Should examples (E14, M11, M16). Make the cycle length a parameter of the calculation module (52 in the app, 4 in E14). Add the test products' expected results to the reference spreadsheet under their own IDs.

**F4 · high · R-14 steps 2–3.** Quote: "Divide each calculation week's sales by the index of its week number". Problem: a week number whose calculation weeks all sold 0 gets index 0, so step 3 divides 0 by 0. A product with only zero sales has a mean of means of 0. The result is NaN or a crash, and R-10 itself expects "products with many zero-sales weeks". Fix: "Seasonal adjustment is not used when any index is 0 or the mean of the means is 0; the note is shown." Add M8.

**F5 · high · R-14, FR-9, FR-20, glossary «Base forecast», R-7, R-8, R-12, FR-24.** Quote: "It is the same value for weeks 1, 2 and 3 unless seasonal adjustment is added", while E14 says "adjusted base forecast 20.216". Problem: the PRD does not say whether seasonal adjustment is a setting (it is missing from FR-20 and «Settings») or is applied automatically wherever every week number has a calculation week. Automatic use would cover almost every 104-week product, including trend products. "Base forecast" names both the deseasonalized value and the per-week forecast. With the adjustment on, R-7, R-8, R-12 and the overview's "week-1 base forecast" (FR-24) can each use either value: E14 with margin 10% and stock 5 suggests 8 or 18. Fix: add a setting «Sesongjustering» (default off) or state that it is automatic. Give the deseasonalized value its own glossary term. State that the week-k base (= normal) forecast is the deseasonalized value × the index of week k, used by R-7, R-8, R-12, FR-24 and the chart. Add M16.

**F6 · medium · §5.6, SM-1, R-9.** Quote: "Calculations use full precision." Problem: the expected values are printed with 3 or 4 decimals (E2 "13.790" against 13.7904231), and the intermediate values are rounded unevenly (13.8172, 13.272). No test tolerance is defined, so each test picks its own. A spreadsheet that uses E14's printed indices gets 10.981 instead of 10.982. Fix: "numbers are compared with an absolute difference below 0.0005; displayed strings are tested separately". Keep full-precision values in the spreadsheet.

**F7 · medium · R-9 display, E13, NFR-5.** Quote: "Forecasts and scenarios are shown with one decimal and a Norwegian decimal comma". Problem: no rounding mode is given. A moving average with window 4 over 10, 10, 10, 11 is exactly 10.25: Python's round (half to even) shows «10,2», while JavaScript's toFixed and Intl (half up) show «10,3». There is no display precision for weeks of cover (E13 prints "0.35" with a point) or for the margin amount on the FR-12 line. Fix: "display rounding is half away from zero; one decimal for forecasts, scenarios and the margin amount; [n] decimals for weeks of cover", and restate E13 in that format. Add M7.

**F8 · medium · FR-12 vs R-8/R-9.** Quote: "Every number on the line equals the value used in the calculation." Problem: the line shows rounded values, but R-8 uses full precision. Take sales 27, 27, 28, moving average 3, margin 10% and stock 30: F1 is 27.333, the margin 2.733, the need 30.067, and the suggested quantity 1. The line «Prognose 27,3 + sikkerhetsmargin 10 % (2,7) − lager 30 = foreslått bestillingsmengde 1» adds up to 0. Fix: show the unrounded remainder before the round-up, for example «= 0,07 → rundet opp til 1». Add M10.

**F9 · medium · FR-13 (Should) vs R-8.** Quote: "calculated with the same rule as FR-11". Problem: the PRD does not say whether the safety margin is added on top of the optimistic and pessimistic values. With the E4 inputs, the quantities are 13 and 10 with the margin, or 11 and 8 without. Fix: write the formula in §5, for example max(0, ⌈round6(F1 × (1 ± s) × (1 + m) − S)⌉), and add M11.

**F10 · medium · §3 «Week» and «Sales history», R-1, R-13, R-14 note, FR-18, E12.** Quote: "a calendar week identified by year and week number" and "the data uses week numbers 1 to 52". Problem: the ISO year 2026 has a week 53. From 2026-W46 to 2027-W02 is therefore 9 weeks (warning) in calendar arithmetic but 8 (no warning) with a 52-week year. The PRD does not say whether week-53 sales count toward the week-52 mean in step 1. Missing weeks (no row) and products whose history ends before the company's latest data week are undefined: zero, stockout, or skipped? It is not stated that sales and stock are whole numbers of 0 or more. A negative stock with forecast 0 would get order-soon status with weeks of cover «–», which R-12 cannot sort. Fix: every product has one row per week up to the latest data week (newer products start later). Week differences use a running index. The generator creates no week 53, or the PRD defines it. Sales and stock are whole numbers of 0 or more. Add M12.

**F11 · medium · R-12.** Quote: "sorts products with order-soon status by weeks of cover, lowest first". Problem: there is no tie-break (every order-soon product with stock 0 has weeks of cover 0) and no order for the other groups. The overview order is therefore not deterministic, although §5 says "the same data and settings always give the same result". Fix: add a tie-break (for example product number) and the order inside every group. Add M14.

**F12 · medium · FR-17 vs FR-19, FR-8, FR-9.** Quote: "Priority: Must for the calculation; Should for the warning." Problem: in the Must scope, a 104-week product with a level shift and no other warning gets High. Once the Should warning exists, it gets Medium, so the Must answer key depends on a Should item. The PRD does not say whether FR-9's "note" or FR-8's window message count as active warnings. Fix: a level shift lowers the label in the Must scope whatever the warning text says. Give a closed list of warnings and notes.

**F13 · medium · R-14 step 4 and «Known limitations».** Quote: "Seasonal adjustment is used only when every week number has at least one calculation week." Problem: a week number with one calculation week gets a deseasonalized value equal to the mean of the means. With exactly one year of calculation weeks, every value is that mean, so the forecast becomes the same week last year (M9: 10, 20, 30, 20 gives 10, 20, 30). This is not listed as a limitation and is not tested. Fix: require two values per week number, or list this as a limitation and add M9.

**F14 · low · FR-11 vs R-9.** Quote: "rounded up to whole units, once" against "the value is rounded to 6 decimals". Problem: there are two roundings, and the mode of the 6-decimal step is not given. Python's round goes half to even; Math.round(x × 1e6) / 1e6 goes half up and adds its own error. Fix: "round to 6 decimals, half away from zero, then round up", and apply the same guard in FR-13 and R-12.

**F15 · low · Glossary «Level shift» and «Unusual week» vs R-11.** Quote: "Three or more consecutive high weeks." Problem: "high weeks" is not defined, and "counting valid weeks only" is missing (a stockout week in between does not break the run, M2). «Unusual week» as defined also covers level-shift weeks, which R-11 says are not unusual. Fix: "Three or more unusual weeks in a row, counting valid weeks only (R-11)", and add "and is not part of a level shift" to «Unusual week».

**F16 · low · Glossary «Valid week», FR-15 vs R-6, FR-8, FR-18.** Quote: "Valid weeks are counted for the thresholds" and "not counted in any threshold". Problem: the window threshold counts calculation weeks, and the 8-week threshold counts the stockout weeks at the end. Fix: name each threshold and what it counts.

**F17 · low · FR-8 vs R-6.** Quote: "gets no moving-average forecast". Problem: this suggests that exponential smoothing could take over, but R-6 says there is no forecast at all. Fix: "gets no forecast".

**F18 · low · FR-20 (inputs to R-4, R-7, R-8).** Quote: "0.1 to 0.9" and "0% to 50%". Problem: it is not stated whether percentages must be whole numbers (NFR-5 covers display only) or which steps of α are allowed (is 0.15 allowed?). Fix: whole percentages, and α in steps of 0.05 or 0.1.

**F19 · low · FR-19 reason text.** Quote: «Middels: 2 utsolgte uker er utelatt.» Problem: when several causes apply, the PRD does not say which are named or in which order, and the FR-26 snapshot tests need one fixed text. Fix: name every cause in a fixed order (amount of data, stockout weeks, unusual weeks, level shift, old data).
